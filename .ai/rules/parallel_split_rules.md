# 并行分工规则 (Parallel Split Rules)

## 适用场景

任一角色在工作过程中发现自己被瓶颈卡住、有独立工作块可以切出去时，可发起一次"并行分工"。不是工作流的固定环节，不强制触发。最终是否拆分由使用者决定，发起方只产出请求说明，不擅自启动并行。

与现有机制的关系：
| 机制 | 适用场景 | 规则文件 |
|------|---------|---------|
| 顺序交接 | 单向流转（PM → Architect → Developer） | workflow.md + 各角色文件 |
| 双向协作 | 两个不同角色间来回对话 | coordination_rules.md |
| 结构化辩论 | 两个 Expert 深度辩论 | ExpertDebate/rules.md |
| 并行分工 | 同角色实例间按文件隔离并行（本规则） | parallel_split_rules.md |

四者独立，互不干扰。

---

## 完整流程

### 1. 发起方自检

发起方跑硬门禁自检（四条逐条判定），再写反问。四条有任一不满足，或反问写不出具体轮次差，直接不出请求，继续单窗口做。

### 2. 产出拆分请求说明

发起方写拆分请求说明，在输出中报告"已产出并行拆分请求，请使用者审阅"。不创建 session 目录，不动任何文件。

### 3. 使用者审阅

- **批准** → 发起方创建 session 目录，补全 context.md 其余区块，使用者将通知话术粘贴至辅助窗口
- **不批准** → 发起方继续单窗口串行，不创建 session

### 4. 两路并行工作

两路各自在隔离分支上工作，辅助方按契约编码，契约变更走 contract_log.md。

### 5. 交付与收尾

见下文"交付与收尾"。

---

## 硬门禁

四条全满足才允许产出请求：

1. **可切出的独立任务 ≥ 4 个**：少于这个数，协调开销（写文档 + 对方起步）很可能超过省下的时间
2. **文件级隔离可达成**：能列出两份不重叠的文件路径清单，列不出来就不切
3. **契约面 ≤ 8 个方法签名**：超过这个数，契约文档本身就变成一个大工程，而且漂移风险急剧上升
4. **发起方保留侧至少有 1 个任务能不等对方独立推进**：如果切完之后自己还得等对方出结果才能动，那不是并行，是换了个地方排队

---

## 反问

发起方必须显式写一句，格式固定：

```
单窗口串行预计 N 轮，切出后预计 M 轮，省 N-M 轮。理由：（具体说明瓶颈在哪）
```

写不出具体轮次差或理由含糊，不出请求。

---

## 拆分请求说明

放在 context.md 顶部，供使用者快速判断是否批准。三部分：

1. **一句话结论**：建议拆分 / 不建议拆分
2. **拆分理由**（3-5 句）：瓶颈在哪、切出去的是什么、切完后两路各自做什么、预计省多少时间
3. **使用者决策点**：固定问句——"请确认是否执行本次拆分。若确认，将通知话术粘贴至辅助窗口；若否，发起方继续单窗口串行。"

---

## 交付状态机

辅助方交付区块维护状态字段，状态流转：

```
未开始 → 编码中 → 测试中 → 已交付
                                    ↘ 异常中断（人工标注）
```

约束：
- 辅助方必须先写完交付说明全部内容，最后一步才把状态改为"已交付"
- "已交付"是单向终态，标记后辅助方不得再修改交付说明和代码
- "异常中断"只能由人工写入，AI 不得自行标注
- 发起方只认"已交付"这一个状态作为收尾信号

---

## 交付与收尾

### 三种情况

**情况一：辅助方先完成，发起方还在做**
- 辅助方写完交付说明，状态改为"已交付"，输出"已交付，等待发起方收尾"，结束
- 不需要通知发起方。发起方做完后读 context.md 交付区块，状态为"已交付"则直接收尾
- 零人工介入

**情况二：发起方先完成，辅助方还在做**
- 发起方读 context.md 发现交付状态不是"已交付"，写完成说明（发起方完成状态改为"已完成"），输出通知话术给辅助方
- 人工将话术粘贴至辅助方窗口
- 辅助方完成后写交付说明，状态改为"已交付"
- 发起方回来收尾（若窗口仍开着则自行读取；若已关闭，人工唤起发起方收尾）

**情况三：双方几乎同时完成**
- 发起方做完后读 context.md 发现辅助方已"已交付"，直接收尾
- 零人工介入

### 发起方收尾步骤

1. 读交付区块确认状态为"已交付"
2. 检视辅助方改动（读分支 diff 或文件清单）
3. 合并辅助方分支——因文件级隔离正常不冲突；若冲突说明隔离被打破，记入 contract_log.md 并人工介入
4. 跑全量测试，确认两路合在一起能通过
5. 逐条核对接口契约区块里的签名与实际代码是否一致（契约一致性检查，最后一道防线）
6. 统一更新正式文档（06_tasks.md 任务状态、CHANGELOG、07_decisions.md）
7. 删除临时 session 目录
8. 输出收尾完成通知告知使用者

## 契约锁定约束

**发起方约束**：接口契约区块里已登记的每个签名都是契约，发起方在实现过程中不得单方面修改。若实现时发现某个签名写不通，必须先做两件事再动代码：①在 contract_log.md 追加一条，写明"旧签名 → 新签名 + 原因"；②在输出中显式报告"契约已变更，请通知辅助方"。追加记录后才可以改代码。每次输出时，若本轮未改契约，也需明确说一句"本轮未变更契约"。此条优先级高于任何编码判断。

**辅助方约束**：辅助方依赖的接口签名以 context.md「接口契约」+ contract_log.md 两个区块为准。若编译报错涉及对方层的接口，第一反应是回去读 contract_log.md 有没有新增条目，而不是自己猜原因或改接口。若发现代码实际签名与契约不符，不得自行调整接口，应在 contract_log.md 追加一条问询（标注"待发起方确认"），然后继续做当前不依赖该接口的其他任务。辅助方无权修改对方文件和接口定义。

**文档更新权**：只有发起方有权限更新正式文档（06_tasks.md / CHANGELOG / 07_decisions.md），辅助方不碰。

## 冲突处理

### 开发中发现（一方需要碰对方文件）

发现方立即停手，不碰那个文件，在 contract_log.md 追加一条，类型标"文件冲突"，写明需要修改的文件、归属对方、原因。然后分两种走法：

- **能通过契约绕开**：冲突的本质是"我的新东西需要对方文件配合注册/接线"。发现方在 contract_log.md 写明请求，然后继续做其他不涉及冲突的任务。对方在自己的节奏里读到记录后处理，处理完标"已解决"。双方不中断，异步传递。
- **绕不开**：同一文件两边都要改业务逻辑，没有契约能绕开。发现方在 contract_log.md 标"需人工介入"，然后继续做不涉及冲突的其他任务。等双方把能做的都做完了，人工介入协调——判断怎么分（文件重新划归某一方，或一方等另一方改完再接），结果写进 contract_log.md，双方继续。

### 合并时发现（git merge 冲突）

发起方收尾合并分支时撞上 git conflict。发起方有合并权，先尝试自行解决冲突：

- 如果是公共文件冲突（入口注册、配置、路由表），发起方直接合并两边改动
- 如果涉及对方文件的具体业务逻辑（发起方看不懂对方为什么那么写），发起方不得猜着改，在 contract_log.md 追加一条标"合并冲突待确认"，保留冲突状态，等辅助方或人工确认

### 要不要打断对方

取决于"这个冲突会不会让对方白费大量工作"。大多数情况下不会——文件隔离保证两路主要工作独立，冲突只是边界摩擦，靠 contract_log.md 异步传递即可，不用中断对方。

只有一种情况需要打断对方：发现方确认契约本身不可行，对方继续做会全部白写。这种情况说明拆分评估有误，走"异常中断"而不是常规冲突处理。

### 公共文件预防

文件归属表里的"公共文件"行不能空着。拆分时如果识别到有公共文件（build.gradle、DI module、路由表等），必须写明谁来改、什么顺序改。合并时才撞上公共文件，说明拆分评估漏了，走"合并冲突"流程。

## 提交身份

并行分工中的提交身份遵循 `.ai/rules/git_rules.md`「提交身份」全局规则，同角色多实例在 `user.name` 和 `user.email` 中加实例后缀（-A / -B）。

context.md 协调约定区块记录两路的 author 身份，方便收尾时核对。通知话术中包含 author 设置指令。

## Session 结构

复用 `.session/{session_id}/` 目录，新增第三种 session 类型"并行分工"，与"协作""辩论"并列。

### 文件

两种文件，不需要 board.md：

- `context.md`：分工方案与交付记录
- `contract_log.md`：append-only 契约变更记录

### context.md 区块顺序（固定）

```markdown
# 并行分工 Session

> Session ID: {session_id}
> 类型: 并行分工
> 创建时间: YYYY-MM-DD
> 发起方: {角色名}
> 辅助方: {角色名}（协助）
> 状态: 进行中（可取值：进行中 | 已收尾 | 异常中断）

- 结论：建议拆分 / 不建议拆分
- 拆分理由：（3-5 句）
- 使用者决策点：请确认是否执行本次拆分。若确认，将通知话术粘贴至辅助窗口；若否，发起方继续单窗口串行。

## 2. 硬门禁自检

1. 可切出独立任务 ≥ 4 个：是 / 否（列出任务数）

3. 契约面 ≤ 8 个签名：是 / 否（列出签名数）
4. 发起方保留侧有 ≥ 1 个独立任务：是 / 否（列出任务）
```

### 通知话术模板

**给辅助方的加入话术**（使用者粘贴至辅助窗口）：

```
你是协助 {发起方角色} 的工程师。请阅读 {context.md 路径}，按其中「文件归属表」和「接口契约」执行。
你的工作范围严格限定在 {辅助方可写路径}，不得修改 {对方可写路径}。
你依赖的接口契约见 context.md「接口契约」区块和 contract_log.md。
若编译报错涉及对方接口，先读 contract_log.md，不要自行改接口。
在 {分支名} 分支开发，完成后跑 {测试命令}。
任何契约变更先追加到 contract_log.md 并通知，不得静默改签名。
开工前先设置 git author：git config user.name '{角色}-{git用户名}-B'，git config user.email '{角色}-{git用户名}-b@{项目域名}'。
交付时在 context.md「辅助方交付」区块写实现摘要（每个改动项的实现方式、关键决策、对发起方的影响），写完后再将状态改为"已交付"。
```

**发起方完成通知话术**（情况二，使用者粘贴至辅助窗口）：

```
发起方已完成工作。请在完成后将交付说明写入 {context.md 路径} 的「辅助方交付」区块，
状态改为"已交付"。
```

**收尾完成通知**（发起方输出，告知使用者）：

```
✅ 并行分工 session {session_id} 已收尾。
辅助方改动已合并，全量测试通过，正式文档已更新。
临时 session 目录已删除。
```
