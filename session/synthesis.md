### 质量门禁

| 阶段流转 | 门禁类型 | 条件 |
|---------|---------|------|
| 想法 → PRD | 🔴 硬门禁 | 00_idea.md 状态"已确认" + 人工确认 |
| PRD → 架构 | 🟢 软门禁 | 01_prd.md 状态"已确认" + 无阻塞项 |
| 架构 → 任务 | 🟢 软门禁 | 02/03/04 状态"已确认" + 无阻塞项 |
| 任务 → 编码 | 🟢 软门禁 | 06_tasks.md 有待办任务 + 无阻塞项 |
| 编码 → 测试 | 🟢 软门禁 | 代码可编译运行 + 无阻塞项 |
| 测试 → Review | 🟢 软门禁 | 09_test_report.md 状态"已确认" + 无阻塞项 |
| Review → 发布 | 🤖 自动门禁 | 测试全部通过 + CHANGELOG 已更新 + 无 Critical 未修复 |

### 设计原则

- **02_architecture.md 膨胀边界**：模板控制在 150 行以内、11 个章节，模板提供框架提示，项目按需展开
- **单一数据源**：状态默认值只在 06_tasks.md 中维护，workflow.md 不重复
- **不新增角色**：DevOps 职责归入 Developer，保持 5 角色体系

## 未解决风险

1. **模板膨胀风险**：分批实施后文件数从 17 增至 18（新增 09_test_report.md），整体仍在可控范围。但未来持续性新增需警惕。
2. **权限变更风险**：06_tasks.md 从"Developer"改为"全员可更新"后，需要确保多个 AI 角色不冲突编辑。建议配合 Git 的细粒度提交来解决。
3. **可观测性依赖**：02_architecture 新增的可观测性章节需要与具体技术栈绑定才有实际价值，模板层面只能提供框架指引。
4. **门禁约束力风险**：质量门禁定义在 workflow.md 中，但没有技术手段强制执行。如果 AI 跳过状态检查直接开工，门禁形同虚设。缓解措施：在 AI 接手检查清单中增加"检查上游文档状态"作为硬性第一步，并使用"绝对禁止"等强约束措辞（参照冲突处理流程的写法）。
